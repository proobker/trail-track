# Named trails and location matching for Trail Track

Researched 2026-10-21. This note distinguishes **identifying a nearby named trail** from **reconstructing the route someone took**. The app currently derives stops from photo locations, routes walking legs between stops through OSRM, and accepts GPX/KML/GeoJSON tracks that retain their shape (`README.md`, `src/routing/route.ts`, `src/import/tracks.ts`).

**Short answer:** Yes, the map can recognize nearby named trails from OpenStreetMap route relations, with USGS as a U.S. supplement. Use that data to suggest a trail and improve the displayed path after confirmation. A few geotagged photos usually cannot prove the exact trail walked, so show uncertainty and favor an imported GPS track when one exists. Better location provenance and accuracy handling is the highest-value prerequisite.

## Recommendation

1. **Keep recorded tracks as the strongest evidence.** If a user supplies GPX/KML/GeoJSON or a dense location history, retain its geometry. A trail catalog can add a name and validate the route, but should not replace the recording.
2. **Use OpenStreetMap (OSM) as the global candidate catalog.** Query nearby walkable ways (`highway=path|footway|track|steps`) and named hiking/foot **route relations**. Relations connect the ways that form an established, often named route, and may include main, alternate, approach, or excursion members. A single way name and a whole route name are different entities. [OSM hiking tagging](https://wiki.openstreetmap.org/wiki/Hiking); [OSM hiking route relations](https://wiki.openstreetmap.org/wiki/Tag:route%3Dhiking).
3. **For a U.S. deployment, consider USGS National Digital Trails as an additional authoritative catalog.** USGS provides nationwide/state downloads and map/feature services; its data is aggregated largely from official sources and published as public-domain geospatial data. It is U.S.-only and has an update lag, so preserve dataset version/date and do not assume it is a live closure feed. [USGS access guide](https://www.usgs.gov/national-digital-trails/how-access-or-view-usgs-trails-dataset-0); [USGS data](https://www.usgs.gov/national-digital-trails/data); [USGS update FAQ](https://www.usgs.gov/national-digital-trails/qas-about-usgs-trail-data).
4. **Show candidates and confidence instead of silently choosing a trail.** For each journey, rank nearby named routes using the number and spacing of located photos, distance to route geometry, chronological order/progress, plausible travel distance/time, and competing nearby routes. Ask the user to confirm when multiple parallel paths fit. This is an implementation inference from the source data model and map-matching guidance below.

## Why photo locations alone are limited

A route relation tells where a trail is mapped, not whether the photographer walked that route. Two photos near the same trail can fit opposite directions, a loop, or several branches. This is especially true when photos are hours apart. Valhalla's map-matching guidance recommends a **continuous GPS trace** with points roughly every 1–10 seconds and warns that larger gaps increase error; its matching API can incorporate timestamps, GPS accuracy, search radius, and route continuity. Thus a photo collection with sparse points should be treated as *candidate trail identification*, not high-confidence map matching. [Valhalla map-matching API and guidance](https://valhalla.github.io/valhalla/api/map-matching/api-reference/).

If the app later records live browser location, `GeolocationCoordinates.accuracy` reports a 95%-confidence horizontal radius in meters. Use it to weight or reject uncertain points, and store it alongside each observation. Precise versus approximate permission also changes the accuracy available on Android. [MDN accuracy property](https://developer.mozilla.org/en-US/docs/Web/API/GeolocationCoordinates/accuracy); [Google Maps SDK Android location permissions](https://developers.google.com/maps/documentation/android-sdk/location).

Photo import choice is decisive. Google states that a Picker `=d` image download retains EXIF metadata **except location metadata**, and the Picker media-item schema does not expose latitude/longitude. The app should explain why Picker photos are unlocated and offer local originals, Google Takeout, a GPX track, or manual placement as alternatives; re-reading the Picker download cannot recover stripped GPS. [Google Photos Picker media download](https://developers.google.com/photos/picker/guides/media-items); [Picker media-item schema](https://developers.google.com/photos/picker/reference/rest/v1/mediaItems).

`src/import/timeline.ts` currently drops observations with reported accuracy above 1,000 m but does not retain the remaining accuracy. `src/model/types.ts` stores photo coordinates and a `locatedBy: 'timeline'` flag, without a general accuracy field or a trail-source ID. Preserve source and accuracy as separate metadata so a low-quality Timeline point cannot carry the same weight as a good EXIF or recorded-track observation. Do not compare confidence radii from different APIs as if they use the same convention: the browser geolocation radius is specified at **95%** confidence, while Android `Location.getAccuracy()` uses **68%**. [MDN browser accuracy](https://developer.mozilla.org/en-US/docs/Web/API/GeolocationCoordinates/accuracy); [Android Location accuracy](https://developer.android.com/reference/android/location/Location#getAccuracy()).

## A practical matching pipeline

The following is a proposed design, not a documented feature of the current app:

1. Build a time-ordered observation set and keep **provenance** (`photo EXIF`, `Takeout sidecar`, `Timeline`, `recorded track`, `manual`). Preserve originals; never overwrite their coordinates with snapped coordinates.
2. Group observations into continuous outings before querying trail data. Expand each outing's bounding box by an accuracy-aware margin and fetch nearby way and hiking/foot relation candidates once per area. OSM's Overpass API supports bounding-box queries and `out geom`; route relations are composed of constituent ways. [Overpass examples](https://wiki.openstreetmap.org/wiki/Overpass_API/Overpass_API_by_Example); [OSM hiking tagging](https://wiki.openstreetmap.org/wiki/Hiking).
3. Filter paths by walkability/access and, where present, difficulty (`sac_scale`) and visibility (`trail_visibility`). OSM access tags can be mode-specific (`foot=*`), and `sac_scale` describes hiking difficulty rather than path visibility. [OSM access tagging](https://wiki.openstreetmap.org/wiki/Access); [OSM sac_scale](https://wiki.openstreetmap.org/wiki/Key:sac_scale).
4. Score whole candidate routes rather than nearest point alone. A strong candidate should account for most photos in chronological sequence with plausible path lengths; penalize large off-route distances, reversals, and missing connections. If evidence is weak, show “near [trail name]” and keep the existing geometry until the user selects a route.
5. For a genuine dense trace, use a walking map matcher. Valhalla can return a snapped shape, matched points, edge names and OSM way IDs; OSRM's Match service also returns tracepoint alternatives and a matching confidence. Neither automatically identifies a complete named hiking *relation* from sparse photos. [Valhalla map-matching API](https://valhalla.github.io/valhalla/api/map-matching/api-reference/); [OSRM Match service](https://project-osrm.org/docs/v26.5.0/http).
6. Cache candidate geometry and names by geographic tile/area and source version; keep only the simplified geometry needed for the current view. This is an architecture recommendation based on public query limits and payload size, not an OSM requirement.

## Service, license, and performance constraints

- **Do not make the public Overpass service a production backend for every map move or import.** Its maintainers describe public instances as suitable for small projects, discourage apps relying on them as a general backend, and advise running an instance or using an appropriate provider for sustained demand. The main public instance gives broad fair-use guidance around 10,000 requests/1 GB per day, with much lower guidance for recurring jobs. Prototype with bounded regional queries; use a hosted or self-run indexed catalog for production scale. [Overpass manual](https://dev.overpass-api.de/overpass-doc/en/preface/commons.html); [OSM Overpass API instance notes](https://wiki.openstreetmap.org/wiki/Overpass_API).
- **Attribute and track OSM licensing.** OSM data is under ODbL: credit OpenStreetMap contributors and review share-alike obligations before distributing a derived trail database. An interactive map can display “© OpenStreetMap contributors” linked to the copyright page. [OSM copyright](https://www.openstreetmap.org/copyright); [OSM legal FAQ](https://wiki.openstreetmap.org/wiki/Legal_FAQ).
- **Do not confuse tiles, geocoding, and trail geometry.** The map background, reverse-geocoded place name, routed line between two stops, and named trail relation are separate data/services. The app currently uses OSRM for walking routes; it does not thereby know which named trail the person used (`src/routing/route.ts`).
- **Keep display data light.** MapLibre recommends removing unused GeoJSON properties, reducing excessive coordinate precision, simplifying line geometry, splitting large datasets, clustering dense points, and avoiding needlessly complex styles. Apply simplification to the *map display copy* of a route while retaining the original imported track. Trail Track already bounds image sizes for thumbnails/lightbox and decodes concurrently; measure import time and map frame rate with realistic large photo sets before raising concurrency or layering a regional trail catalog. [MapLibre large-data guide](https://maplibre.org/maplibre-gl-js/docs/guides/large-data/).

## Suggested first increment

Add a non-destructive **“Find nearby trails”** action on a selected walking journey. Fetch bounded OSM candidates for the journey extent, show names and preview lines with source attribution, let the user select or dismiss a match, and store the selected source ID/name separately from the journey's original route geometry. Measure candidate lookup time, number of candidates, and user corrections before automating any snapping. This is an implementation recommendation, not a claim about external services.

## Codebase priorities

1. **Model evidence quality first:** extend `src/model/types.ts` and import paths with location source, optional horizontal accuracy, and original versus inferred coordinates. EXIF GPS does not necessarily include a usable accuracy radius, so represent missing accuracy explicitly. `src/import/timeline.ts` currently rejects accuracy above 1,000 m then discards accepted values.
2. **Revise stop clustering:** `src/trail/cluster.ts` uses a 100 m default radius, expanded for related scenes. Nearby parallel trails or switchbacks can fall inside that radius. Treat the radius as a grouping heuristic; incorporate available accuracy, time, and candidate path topology when evaluating whether photos share a stop.
3. **Place unlocated photos along real geometry:** `src/trail/placeUnlocated.ts` currently interpolates latitude and longitude between stop centers. Once a user has selected a trail or imported a track, interpolate by progress along that geometry when timestamps and endpoints make the placement credible; otherwise label the marker as approximate.
4. **Preserve source-specific import guidance:** Picker downloads omit location EXIF, so keep Takeout/local originals/track import prominent for trail reconstruction. [Google Photos Picker media download](https://developers.google.com/photos/picker/guides/media-items).
5. **Profile performance before changing it:** apply the MapLibre large-data techniques to candidate overlays as they grow, but there is no measured map bottleneck in this research. One code-inspection hypothesis is `src/map/MapView.tsx`: playback progress changes cause full `trail` and `stops` GeoJSON to be sent with `setData` again even though those sources are static for a journey. MapLibre documents that `setData` updates a source and re-renders the map. Benchmark playback frame rate on a long journey, then update static sources only when the journey changes if this proves material. Also measure import time, memory, and candidate-query latency before choosing a cache or tile strategy. [MapLibre GeoJSON source API](https://maplibre.org/maplibre-gl-js/docs/API/classes/GeoJSONSource/); [MapLibre large-data guide](https://maplibre.org/maplibre-gl-js/docs/guides/large-data/).
